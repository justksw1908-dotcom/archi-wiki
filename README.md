# 건축공학 학습 위키 — 웹앱 (Phase 1~9 + 로드맵 이후 추가 기능)

로드맵의 Phase 1(데이터 모델)·Phase 2(개발 환경)·Phase 3(파일 업로드·텍스트 추출)·Phase 4(AI 위키 자동 생성)·Phase 5(위키 열람 UI)·Phase 6(퀴즈 생성·풀이)·Phase 7(망각곡선 복습 스케줄러)·Phase 8(Ollama 로컬 폴백)·Phase 9(배포·모바일 접속) 산출물.

원래 로드맵(0~9 총 10단계)은 2026-08-24에 폰 접속까지 실제로 확인되어 **전부 끝났어요**. 지금부터는 로드맵 이후에 추가로 요청하신 것들을 "Phase 10"이라는 이름으로 이어서 정리해요(정식 로드맵 번호는 아니고, 그냥 이후 작업을 구분하려고 붙인 이름이에요).

## 지금 상태

- **Supabase 스키마** (`supabase/schema.sql`, `supabase/storage.sql`, `supabase/migrations/002_phase4_pending_changes.sql`): source_files → text_chunks → wiki_pages → wiki_links / quiz_items → quiz_attempts 6개 계층 + images 보조 표 + pending_changes(AI 제안 승인 대기열), 그리고 원본 파일을 담을 Storage 버킷(`source-files`). 전부 RLS(행 단위 보안)로 로그인한 본인 데이터만 접근 가능 — 로컬 Postgres에 실제로 실행해서 DB 쪽 FK 체인·검색 인덱스·역링크·RLS 격리, Storage 쪽 폴더별 접근 격리까지 전부 재현해서 확인함.
- **Next.js 16 (App Router, TypeScript, Tailwind)** 프로젝트 골격: Supabase 클라이언트, 아이디+비밀번호 로그인(Phase 10에서 이메일 매직 링크를 대체함 — 아래 참고), 접근 제어(`src/lib/supabase/middleware.ts`)까지 완료. 사용자 본인이 실제 Supabase 프로젝트로 Phase 2 완료(`/api/dev-check` 성공)까지 확인함.
- **Phase 3: 파일 업로드 · 텍스트 추출** (`/upload` 페이지, `/api/files/upload`): PDF·TXT를 올리면 Storage에 원본을 저장하고, 텍스트를 뽑아 문단 단위로 청크를 나눠 `text_chunks`에 저장해요. 실제 워크북 PDF 7개 전부로 추출·청킹을 검증했고, 그 과정에서 PDF 하나(0장)의 "※" 기호가 제어문자로 깨져 나와 DB 저장 자체가 실패하는 버그를 발견해서(로컬 Postgres로 실제 재현) 고쳤어요 — 지금은 그 파일도 정상 저장돼요.
- **Phase 4: AI 위키 자동 생성** (`/upload` 페이지의 "AI로 위키 문서 생성 시작" 버튼, `/api/wiki/generate`, `/pending` 페이지, `/api/pending`): 저장된 텍스트 조각을 Gemini(`gemini-3.6-flash`)로 읽어서 위키 문서 후보를 뽑아요. 미리 정한 3단계 권한 모델대로 동작합니다.
  - **완전히 새로운 개념**은 승인 없이 바로 `wiki_pages`에 문서로 만들어져요.
  - **기존 문서와 겹치지만 추가할 내용이 있는 경우(extend)** 또는 **기존 문서 내용이 틀렸다고 판단되는 경우(edit)**는 자동으로 반영되지 않고 `pending_changes`(승인 대기열)에 쌓여요. `/pending` 페이지에서 사람이 직접 승인해야만 실제 문서가 바뀝니다. 승인 시 extend는 기존 내용에 새 내용을 덧붙이고, edit는 AI가 제안한 내용으로 교체해요. 거절하면 문서는 그대로 남고 제안만 사라져요.
  - AI는 **텍스트만** 읽어요 — 이미지·표·그림에 대한 언급은 무시하도록 프롬프트에 명시했고, 이미지 삽입은 사용자가 직접 하는 걸 전제로 해요(이미지 처리는 이후 단계).
  - 한 번 호출에 청크 2개씩만 처리해요(서버리스 함수 실행 시간 제한 때문). `/upload` 페이지 버튼을 누르면 다 끝날 때까지 자동으로 반복 호출해요. 이미 처리한 청크(`text_chunks.processed_at`)는 다시 돌려도 중복 생성/중복 과금이 안 나요.
  - DB에 실제로 반영되는 로직(신규 생성·링크 연결·승인 대기열 등록·승인 시 병합·거절·RLS로 다른 사용자 격리)은 로컬 Postgres에 스키마를 그대로 올리고 값을 넣어 전 과정을 재현해서 검증했어요. 다만 Gemini API 자체 호출은 API 키가 있는 실제 환경에서만 테스트할 수 있어서, 이 부분은 사용자가 직접 확인해야 해요.
- **기존 위키(1104개 문서) 일괄 이식** (`supabase/data-import/`): 이전에 만든 HTML 프로토타입 위키를 AI 재생성 없이 그대로 실제 DB로 옮기는 1회성 SQL 스크립트예요. 지금부터는 이 7개 장(0장~6장)은 완성된 걸로 보고, AI 자동 생성(Phase 4)은 나중에 새로 추가하는 자료에만 써요. 실행 순서와 방법은 `supabase/data-import/README.md` 참고. 로컬 Postgres로 전체 이식·정리 과정(AI로 테스트 생성했던 문서 정리 → 1104개 이식 → 링크 1523개 연결)을 재현해서 최종 개수·중복·깨진 링크 없음까지 확인했어요.
- **Phase 5: 위키 열람 UI** (`/wiki`, `/wiki/[id]`): DB에 있는 위키 문서를 실제로 읽고 넘나드는 화면이에요.
  - `/wiki`: 검색어(제목·본문)나 장(0장~6장)을 골라서 문서를 찾아요. 아무것도 안 고르면 장별 문서 개수만 보여주고 목록은 안 띄워요(1104개를 한 번에 다 보여주면 느리고 압도적이라서).
  - `/wiki/[id]`: 문서 본문·포인트를 보여주고, **관련 문서**(이 문서가 링크한 다른 문서)와 **역링크**(이 문서를 참조하는 다른 문서)를 각각 클릭해서 넘나들 수 있어요.
  - 문서마다 **편집** 버튼이 있어서 AI가 잘못 정리한 내용이나 오탈자를 직접 고칠 수 있어요(분류·제목·정의·포인트·관련 문서·재확인 필요 표시). 이건 AI 승인 대기열(`/pending`)과는 별개로, 사람이 직접 고치는 거라 승인 절차 없이 바로 반영돼요. 관련 문서 목록을 저장하면 기존 링크는 지워지고 새로 적은 목록으로 완전히 교체돼요.
  - 문서 추가·삭제 화면은 아직 없어요(범위를 "AI가 잘못 정리한 내용을 고치는 최소한의 편집"으로 좁혔어요) — 필요하면 다음에 추가할 수 있어요.
  - DB에 실제로 반영되는 로직(수정 저장, 관련 문서 목록 완전 교체 시 역링크가 정확히 갱신되는지, 존재하지 않는 제목은 조용히 건너뛰는지, 검색이 실제로 매치하는지)은 로컬 Postgres로 재현해서 확인했어요.
- **Phase 6: 퀴즈 생성 · 풀이** (`/quiz`, `/quiz/practice`, `supabase/migrations/003_phase6_quiz_helpers.sql`): 위키 문서마다 AI가 퀴즈를 한 번만 만들어 `quiz_items`에 캐싱해두고, 풀 때는 **AI를 다시 부르지 않고 코드로만 채점**해요.
  - `/quiz`: 퀴즈 생성 현황(문서 몇 개 중 몇 개에 퀴즈가 있는지)을 보여주고, "장 · 절 · 문서 골라서 퀴즈 생성" 버튼으로 `/quiz/select`로 이동해요.
  - `/quiz/select`: 전체를 한 번에 만들면 Gemini 할당량을 거의 다 써버릴 수 있어서, **장·절·개별 문서 단위로 직접 범위를 골라서** 그 범위만 생성하도록 바꿨어요. 전체 선택 체크박스, 장 단위 체크박스, 절 단위 체크박스, 문서 하나씩 체크박스가 모두 있고 상위 체크박스는 하위 선택 상태에 따라 부분 선택(가로줄) 표시가 돼요. 이미 퀴즈가 있는 문서는 "생성됨"으로 표시되고 체크박스가 비활성화돼서 다시 못 고르게 막아뒀어요. 선택 후 생성 버튼을 누르면 한 번에 3문서씩 나눠서 순차 호출하고, 진행 상황(몇 개 중 몇 개 처리, 생성된 문항 수)이 화면에 실시간으로 표시돼요.
  - **버그 수정(2026-08-23)**: `/quiz/select`에 6장이 아예 안 보이는 문제가 있었어요. 원인은 Supabase REST API가 한 번의 조회에 기본 최대 1000행까지만 돌려주는데(대시보드 Settings → API → Max Rows, 기본값 1000), 문서 전체가 1104개(1000개 초과)라 정렬 순서상 뒤쪽인 6장이 잘려서 안 왔던 거예요(SQL Editor로 직접 `count(*)`를 봤을 땐 이 한도를 안 거쳐서 1104개가 다 보였던 것). `src/lib/supabase-paginate.ts`에 1000개씩 끝까지 나눠 가져오는 공용 함수(`fetchAllRows`)를 만들어서 `/api/quiz/scope`, `/wiki` 목록의 장별 개수, `/quiz` 허브의 "퀴즈 있는 문서 수" 세 곳 모두 이 함수로 바꿨어요(뒤의 두 곳도 데이터가 느는 대로 같은 문제를 겪을 수 있어서 같이 고쳤어요).
  - **Gemini 무료 등급 일일 한도 안내(2026-08-23)**: Google이 최근 무료 등급 일일 요청 수를 모델당 **하루 20회**로 크게 줄였어요(문서 1개 = 보통 요청 1회). `/quiz/select`에서 한 번에 20개 넘게 고르면 도중에 반드시 걸려요. 걸리면 앱이 자동으로 감지해서: (1) 이미 성공한 문서는 그대로 저장돼 있고, (2) 남은 문서는 API를 더 부르지 않고 바로 멈추고, (3) 화면에 "오늘의 무료 API 할당량을 다 썼어요"라는 안내와 함께 선택 목록을 그대로 남겨둬요 — 태평양 시간 자정(한국 시간 대략 오후 4~5시경)에 초기화되니, 그때 `/quiz/select`에서 "생성" 버튼만 다시 누르면 이어서 만들어져요. 그래서 한 번에 15개 안팎(절 1~2개 정도)씩, 하루에 한 번쯤 나눠서 생성하는 걸 추천해요.
  - 문제 형식은 객관식(4지선다)·OX·빈칸 채우기·서술형 4가지예요. 이미지 인식·관계 퀴즈는 이미지 업로드 기능이 아직 없어서 이번 범위에서 뺐어요.
  - `/quiz/practice`(전체 또는 `/quiz/practice?chapter=N`으로 장별): 무작위로 최대 10문제를 뽑아 하나씩 풀어요. 제출하면 서버가 즉시 채점해서 정답 여부를 보여줘요 — 서술형·빈칸도 AI를 다시 부르지 않고, 생성 시점에 같이 저장해둔 "허용 표현 목록"과 정확히 대조하는 방식으로 채점해요(공백·대소문자 차이는 무시).
  - 채점 결과는 `quiz_attempts`에 기록돼요. Phase 7부터 이 기록에 망각곡선(SM-2) 계산이 실제로 붙었어요 — 아래 참고.
  - "무작위 문제 뽑기"는 DB 함수(`get_random_quiz_items`)로 처리했어요 — 문서가 1104개나 되다 보니 "이 목록에 없는 것들" 같은 조건을 앱 코드에서 직접 만들면 요청이 너무 길어져 실패할 수 있어서, Postgres 쪽에서 한 번에 처리하도록 옮겼어요. (`get_wiki_pages_without_quiz` 함수는 예전 "전체 일괄 생성" 방식에서 쓰던 건데, 지금은 `/quiz/select`가 전체 목록 + 생성 여부를 직접 조회해서 화면에서 걸러내는 방식으로 바뀌어서 더 이상 안 써요 — DB에는 그대로 남아있지만 무해하니 지우지 않아도 돼요.)
  - 로컬 Postgres로 DB 함수(무작위 문제 뽑기 — 정답 컬럼은 절대 안 내려주는지, 장 필터가 정확한지)와 새 선택 생성 흐름(범위 조회, 이미 만든 문서 재확인 후 건너뛰기, 삽입)의 RLS 격리(다른 사용자의 id를 넣어도 아예 안 보이는지)를 확인했고, 채점 로직(정확히 일치·허용 표현·공백 차이 등 11가지 경우)도 별도로 검증했어요.
- **Phase 7: 망각곡선 복습 스케줄러** (`/quiz/review`, `src/lib/sm2.ts`, `supabase/migrations/004_phase7_review_scheduler.sql`): 퀴즈를 풀 때마다 SM-2 알고리즘으로 "다음엔 언제 다시 볼지"를 계산해서 `quiz_attempts`에 같이 기록하고, 그 일정에 맞춰 오늘 복습할 문제만 모아서 보여줘요.
  - **SM-2 계산은 AI를 전혀 안 씁니다** — `src/lib/sm2.ts`의 순수 함수가 (이전 상태, 이번 정오답)만 보고 다음 상태를 계산해요. 정답/오답만 있는 우리 데이터를 SM-2 원안의 0~5점 품질 점수로 단순 매핑했어요(맞으면 5점, 틀리면 2점 — 2점은 SM-2 기준상 "재시작"에 해당해서, 틀리면 반복 횟수가 0으로 리셋되고 내일 다시 나와요). 맞을 때마다 간격이 늘어나요(1일 → 6일 → 그 이상은 간격×숙련도로 계산).
  - `quiz_attempts`는 풀 때마다 한 줄씩 쌓이는 로그 표라서, 문제 하나의 "지금 상태"는 그 문제의 가장 최근 시도 행이에요. `/api/quiz/attempts`가 채점 직전에 그 최신 행을 찾아서 다음 상태를 계산하고, 새 시도 행에 같이 저장해요.
  - `/quiz` 허브에 "오늘의 복습" 카드가 생겨서 오늘 다시 볼 차례인 문제 수가 바로 보여요. "복습 시작"을 누르면 `/quiz/review`로 가서 그 문제들만(무작위가 아니라 밀린 것부터 우선) 풀어요 — 채점은 연습 모드와 완전히 같은 경로(`/api/quiz/attempts`, AI 재호출 없음)를 타고, 제출할 때마다 "다음 복습은 N일 후예요"가 같이 떠요. 이 안내는 `/quiz/practice`(무작위 연습)에서도 똑같이 보여요 — 연습이든 복습이든 결국 같은 SM-2 일정에 반영되니까요.
  - "오늘 복습할 문제 찾기"도 `get_random_quiz_items`와 같은 이유로 DB 함수(`get_due_review_items`, `count_due_review_items`)로 처리했어요 — 문서 수가 많아 앱 코드에서 직접 거르면 느려질 수 있어서요.
  - 로컬 Postgres로 검증: 문제별 최신 시도만 정확히 골라내는지(같은 문제를 여러 번 풀었을 때 오래된 기록이 아니라 최신 기록 기준으로 판단하는지), 한 번도 안 푼 문제가 "오늘 복습 대상"으로 잡히는지, 미래 일정인 문제는 빠지는지, 밀린(어제 이전) 일정도 포함되는지, RLS 격리, 그리고 방금 채점한 문제가 다음 조회에서 바로 빠지는 전체 흐름(라운드트립)까지 확인했어요. SM-2 계산 자체도 알려진 계산값(연속 정답 시 EF·간격 변화, 오답 시 리셋, EF 하한 1.3 클램프)과 대조하는 별도 테스트로 검증했어요.
- **Phase 8: Ollama 로컬 폴백** (`src/lib/ollama.ts`, `src/lib/ai-quota.ts`): Gemini 무료 할당량(하루 20회)을 다 썼을 때, 컴퓨터에 [Ollama](https://ollama.com)가 설치되어 켜져 있으면 **자동으로** 그쪽으로 넘어가서 위키 생성(`/api/wiki/generate`)·퀴즈 생성(`/api/quiz/generate`)을 이어가요. 아무것도 따로 설정할 필요 없이 그냥 켜두기만 하면 돼요.
  - 어떻게 동작하는지: Gemini가 429(할당량 초과) 오류를 주면, 이 서버가 지금 실행되고 있는 컴퓨터의 `localhost:11434`(Ollama 기본 주소)로 아주 짧게(1.5초) 살아있는지 확인해요. 응답이 있으면 같은 프롬프트·같은 JSON 스키마로 로컬 모델에게 대신 만들어달라고 하고, 결과를 Gemini 응답과 똑같은 방식으로 검증·저장해요. 응답이 없으면(Ollama가 꺼져있거나, 배포된 서버에서 폰으로 접속한 경우처럼 애초에 같은 컴퓨터가 아니면) 조용히 원래의 "할당량 초과" 안내로 넘어가요 — 에러가 나거나 멈추지 않아요.
  - **로컬(`npm run dev`)에서 자기 컴퓨터로 쓸 때만 실질적으로 동작**해요. Phase 9에서 Vercel 등에 배포하면, 배포된 서버는 사용자 개인 컴퓨터의 Ollama에 물리적으로 닿을 수 없어서(다른 기계니까) 이 폴백은 자동으로 비활성화된 것처럼 동작해요(오류 없이, 그냥 할당량 초과 안내만 나와요) — 이게 "기능을 못 쓰는 환경이면 안내만 하고 우아하게 넘어간다"는 처음 요구사항 그대로예요.
  - 설정: Ollama를 설치하고(https://ollama.com) 아무 모델이나 하나 받아두세요 — 기본값은 `llama3.1`이고, `ollama pull llama3.1`로 받거나 `.env.local`에 `OLLAMA_MODEL`을 다른 모델명으로 지정하면 그 모델을 써요(예: `qwen2.5:7b`). 주소를 바꾸고 싶으면 `OLLAMA_BASE_URL`도 설정할 수 있어요(기본값 `http://localhost:11434`). 둘 다 선택사항이라 안 정해도 앱은 정상 동작하고, 그냥 Ollama 폴백만 안 켜져요.
  - `/quiz/select`의 진행 상황과 `/upload`의 생성 진행 상황에 "로컬 Ollama로 만든 것 N개 포함"이 표시돼서, 실제로 폴백이 쓰였는지 바로 알 수 있어요.
  - 이 김에 발견해서 같이 고친 버그: `/api/wiki/generate`가 기존 문서 제목 전체를 가져올 때도 Phase 6에서 겪었던 것과 같은 PostgREST 1000행 한도에 걸려 있었어요(문서 1104개 중 뒤쪽 제목이 누락돼서, 이미 있는 개념을 새로 또 만들거나 extend/edit 대상을 못 찾을 수 있던 버그) — `fetchAllRows`로 고쳤어요. 그리고 `/upload`의 생성 루프가 할당량 초과 시 멈추지 않고 계속 재호출하던 잠재적 무한 루프도 이번에 같이 고쳤어요(Phase 6에서 `/quiz/select`는 이미 고쳤는데 `/upload` 쪽은 그때 안 건드렸었어요).
  - 로컬에선 실제 Ollama가 없어서(이 환경엔 GPU/모델이 없음) 진짜 로컬 모델로 문제를 생성해보는 것까진 확인 못 했고, 대신 Ollama API 규격에 맞춘 가짜 서버를 띄워서 클라이언트 코드가 실제로 정확히 그 규격대로 요청·응답을 주고받는지(모델명·JSON 스키마·응답 파싱), 할당량 아닌 오류는 폴백을 안 쓰고 그대로 전파되는지, 할당량 초과인데 폴백도 실패하면 배치를 막지 않고 일반 오류로만 처리되는지, 그리고 (Ollama가 이 환경처럼 정말 없을 때) 빠르게 "사용 불가"로 판단하고 원래 할당량 초과 안내로 넘어가는지까지 확인했어요. 사용자 컴퓨터에서 실제 Ollama로 하는 최종 확인은 직접 해주셔야 해요.
- **Phase 9: 배포(Vercel) · 모바일 접속** — 로드맵의 마지막 단계예요. 코드 쪽은 이미 배포 가능한 상태였어요(확인한 것들: 로그인 리다이렉트 주소가 `window.location.origin`으로 그때그때 계산돼서 어디에 배포하든 따로 코드를 안 고쳐도 됨, 환경변수는 전부 요청 처리 중에 읽어서 빌드 자체는 값이 없어도 실패하지 않음, 이미지·파일 처리에 로컬 디스크 저장을 쓰는 곳이 없어서 서버리스 환경과도 궁합이 맞음, Vercel Hobby(무료) 플랜의 함수 실행 제한이 기본 5분이라 AI 호출 몇 초는 전혀 문제 없음) — 그래서 새로 바뀐 코드 파일은 없고, 이번엔 아래 15~16번의 **배포 설정** 자체가 할 일이에요.
  - Ollama(Phase 8)는 배포된 서버에서는 자동으로 안 켜져요 — Vercel 서버는 선웅님 컴퓨터의 `localhost:11434`에 물리적으로 닿을 수 없어서, 배포 후엔 할당량 초과 시 항상 "할당량 초과" 안내만 뜨고 로컬 개발(`npm run dev`)할 때만 폴백이 실제로 동작해요. 처음 설계했던 "기능을 못 쓰는 환경이면 조용히 안내만 하고 넘어간다"는 요구사항 그대로예요.
  - `.env.local`의 `OLLAMA_BASE_URL`/`OLLAMA_MODEL` 두 줄은 배포 환경(Vercel)에는 아예 등록하지 않아도 돼요 — 등록해봐야 그 값이 가리키는 주소(선웅님 컴퓨터)에 서버가 닿을 수 없어서 효과가 없고, 안 켜져 있어도 앱이 오류를 내지 않고 우아하게 넘어가니 안전해요.
- **Phase 10: 아이디/비밀번호 로그인 + 위키 공개 열람** (로드맵 완료 후 추가 요청):
  - **로그인 방식**: 이메일 매직 링크를 없애고 **아이디 + 비밀번호**로 바꿨어요. Supabase가 기본 제공하는 "이메일+비밀번호" 로그인을 그대로 쓰되, 아이디(이메일 형태가 아닌 진짜 아이디, 예: `sunwoong`)를 내부적으로 `아이디@archi-wiki.local`이라는 가짜 이메일로 바꿔서 Supabase에 전달해요(`src/lib/auth-username.ts`). 실제로 메일이 오가는 주소가 아니라 로그인 식별자로만 쓰여서, 예전에 겪으신 "이메일 레이트 제한" 문제도 이제 아예 안 생겨요. 기존 계정의 `user_id`는 그대로 유지돼서 지금까지 쌓인 위키 문서·퀴즈 기록에는 전혀 영향 없어요. (참고: 이제 이메일을 통한 로그인 절차 자체가 없어져서, Phase 9에서 설정했던 Supabase의 Site URL/Redirect URLs는 로그인 자체에는 더 이상 관여하지 않아요 — 나중에 "비밀번호 찾기" 같은 이메일 기반 기능을 추가하게 되면 그때 다시 의미가 생겨요.)
  - **위키는 로그인 없이 열람 가능**: `/wiki`, `/wiki/[id]`는 이제 누구나(로그인 안 해도) 볼 수 있어요. `wiki_pages`/`wiki_links`에 "누구나 읽기 가능" RLS 정책과 GRANT를 추가했고(`supabase/migrations/005_phase10_public_wiki_read.sql`), 쓰기(수정·삭제·추가)는 여전히 로그인한 본인만 가능하도록 그대로 뒀어요 — 로컬 Postgres로 비로그인(anon) 사용자가 읽기는 되고 쓰기는 전부 막히는지, 로그인한 사용자도 남의 문서는 못 고치는지까지 직접 재현해서 확인했어요.
  - **편집과 AI 생성은 계속 로그인 필요**: 문서 편집 저장(`PATCH /api/wiki/pages/[id]`), AI 위키 생성(`/api/wiki/generate`), AI 퀴즈 생성(`/api/quiz/generate`)은 전부 그대로 로그인이 있어야 동작해요 — 접근 제어 미들웨어(`src/lib/supabase/middleware.ts`)에서 한 번, 각 API 라우트 자체의 로그인 확인에서 또 한 번, DB의 RLS 정책에서 또 한 번, 이렇게 세 겹으로 막혀 있어요. `/wiki/[id]`에서도 로그인 안 했으면 편집 버튼 자체가 안 보이고 "로그인하면 편집할 수 있어요" 안내만 떠요.
  - **계정에 아이디/비밀번호 설정하기**: 매직 링크로 이미 로그인해본 계정이 하나 있다는 전제로, `scripts/set-login-credentials.ts`라는 1회성 관리자 스크립트로 그 계정에 아이디·비밀번호를 얹어요(새로 회원가입하는 게 아니라, 기존 계정의 로그인 방식만 바꾸는 거예요). 아래 "시작하려면" 17번 참고.
- **Phase 10 후속: 홈이 위키로, 퀴즈 풀이도 공개** (연이어 추가 요청받음):
  - **접속하면 바로 위키**: `/`(홈)이 이제 `/wiki`로 바로 넘어가요. 예전에 홈에 있던 "위키/업로드/승인대기/퀴즈" 링크와 로그인 상태 표시는 모든 화면 맨 위에 공통으로 뜨는 내비게이션 바(`src/app/NavBar.tsx`)로 옮겼어요. 업로드·승인대기 링크는 로그인했을 때만 보여요. 로그아웃 버튼도 여기 새로 생겼어요(예전엔 로그아웃할 방법 자체가 없었어요).
  - **퀴즈 "풀이"도 이제 로그인 없이 가능**: `/quiz`, `/quiz/practice`는 로그인 안 해도 문제를 풀고 채점 결과를 바로 볼 수 있어요. 다만 비로그인 상태로 푼 건 기록이 안 남아요(정답/오답 이력도, 망각곡선 복습 일정도 저장 안 됨) — `quiz_attempts`는 로그인한 계정 것만 저장할 수 있는 구조라서, 결과 화면에 "로그인하면 이 결과가 복습 일정에 저장돼요"라고 안내가 떠요. **막혀 있는 건 여전히 "생성"뿐이에요**: 장·절·문서 골라서 새 퀴즈 만들기(`/quiz/select`, `/api/quiz/generate`)와, 개인 기록을 바탕으로 한 복습(`/quiz/review` — 비로그인이면 "내 기록"이라는 게 없어서 애초에 의미가 없어요)은 그대로 로그인이 필요해요.
  - DB 쪽 변경: `get_random_quiz_items` 함수가 원래 "이 문제가 내 것인지" 확인하던 걸 없애고(이 앱은 사용자가 한 명뿐이라 의미가 없어서) 누구나 부를 수 있게 했어요(`supabase/migrations/006_phase10b_public_quiz_practice.sql`). 정답 자체는 이 함수도, `quiz_items` 테이블 직접 조회도 여전히 막혀 있어서(비로그인 사용자가 개발자 도구로 정답을 미리 볼 수 없어요), 채점은 서버가 별도 권한(서비스 롤)으로 그 문제 하나만 확인해서 처리해요 — 로컬 Postgres로 "비로그인은 조회만 되고 쓰기는 전부 막히는지", "함수로는 정답이 안 나오는지", "테이블을 직접 조회하면 여전히 permission denied인지"까지 확인했어요.
  - 이제 안 쓰는 파일: `src/app/auth/callback/route.ts`(매직 링크 콜백 처리용이었는데, 더는 매직 링크를 안 써서 무해하지만 필요 없어졌어요) — 지우고 싶으시면 지우셔도 되고, 그냥 두셔도 아무 문제 없어요.
- **Phase 10 후속: 화면 디자인** (로드맵 이후 세 번째 추가 요청): "학습도구답게 밝고 친근하게, 흰색 + 붉은~주황 계열, 나무위키/위키피디아(위키 기능) · SK하이닉스(디자인) 참고"라는 방향을 먼저 시안(모든 화면을 대표하는 3장짜리 디자인 캔버스, 위키 목록·문서 상세·퀴즈 풀이)으로 보여드리고 승인받은 뒤 실제 코드에 적용했어요.

- **Phase 10 후속: 퀴즈 절 선택 + 위키 미리보기 + AI 에이전트 + Groq 폴백** (디자인 확인 후 네 번째 추가 요청, 2026-08-24):
  1. **퀴즈를 장뿐만 아니라 절 별로도 골라서 풀 수 있게** — `/quiz`의 "퀴즈 풀기"·"장·절 골라서 복습"이 이제 장을 펼치면 그 안의 절들이 같이 나와서, "2장 전체"뿐 아니라 "2장 1절"처럼 더 좁혀서 풀 수 있어요(`QuizLinks.tsx`, `supabase/migrations/007_phase10c_quiz_section_filter.sql`). `/quiz/practice`·`/quiz/review` URL에 `?chapter=2&section=1`처럼 붙어요.
     - **겸사겸사 발견해서 고친 버그**: 위키 문서의 "분류(section)" 문자열이 장마다 형식이 조금씩 달랐어요 — 대부분은 `"N장 · N절 · 소제목"`인데, **2장만 유독** `"2장 · I 콘크리트재료 · 1절 · 시멘트 · 소제목"`처럼 장과 절 사이에 대분류가 하나 더 껴 있었어요. 예전 로직은 "장 바로 다음에 절이 온다"고 가정하고 있어서, 2장 문서 268개 전부가 "절 없음" 취급되고 있었어요(`/quiz/select`의 절 아코디언에서도 2장만 절 구분이 안 됐던 것도 같은 원인). 장 번호는 맨 앞에서, 절 번호는 문자열 어디에 있든 따로 찾도록 고쳤어요(`src/lib/parse-section.ts`) — 이번에 새로 생긴 절 선택 기능뿐 아니라 기존 `/quiz/select`의 절 구분도 같이 정확해졌어요. 로컬 Postgres에 2장처럼 장·절 사이에 대분류가 낀 문서, "11절"처럼 두 자리 절 문서를 직접 넣어서 "1절"을 선택했을 때 "11절"이 잘못 같이 딸려오지 않는지까지 확인했어요.
  2. **위키 개념 클릭 시 바로 이동하지 않고 먼저 펼쳐서 보여주기** — `/wiki` 목록의 문서 카드와 `/wiki/[id]`의 "관련 문서"·"이 문서를 참조하는 문서"를 클릭하면, 이제 바로 다른 페이지로 이동하지 않고 그 자리에서 카드가 펼쳐지면서 정의·포인트를 먼저 보여줘요. 그걸로 부족하면 펼쳐진 내용 안의 "자세히 보기 →" 링크를 눌러야 실제로 그 문서 페이지로 이동해요(`WikiResultCard.tsx`, `RelatedDocsPanel.tsx`). 이미 목록/상세 조회 시점에 필요한 내용을 같이 가져와 두기 때문에, 펼칠 때 추가로 서버에 다시 물어보지 않아요.
  3. **위키 우측 하단 AI 에이전트 채팅** — 문서를 보다가 궁금한 걸 가볍게 물어볼 수 있는 채팅 위젯이 모든 위키 화면 오른쪽 아래에 떠요(`AgentChatWidget.tsx`, `POST /api/agent/chat`). 버튼을 누르면 기존 화면 여백을 벗어나지 않는 고정 크기 패널(최대 340×460px 정도)이 열려요. `/wiki/[id]` 문서 페이지에서 열면 **지금 보고 있는 문서의 제목·분류·정의·포인트를 참고해서** 답하고(문서 인식형), `/wiki` 목록에서 열면 특정 문서 없이 일반적으로 답해요. 위키 열람 자체와 달리 이 채팅은 **로그인이 필요**해요(비로그인 사용자가 무료 API 할당량을 소진하는 걸 막기 위해 — 기존 AI 생성 기능들과 같은 이유) — 로그아웃 상태에서 위젯을 열면 로그인 안내만 뜨고 로그인하면 바로 대화할 수 있어요. 이 기능은 Gemini가 아니라 **Groq**를 써요(아래 4번 참고) — Groq API 키가 없으면 위젯은 뜨지만 "AI 에이전트가 아직 설정되지 않았어요"라는 안내만 나와요.
  4. **무료 AI API 조사 + Groq를 새 폴백으로 추가** — Gemini 무료 등급이 최근 하루 20회로 크게 줄어든 것에 대해, 다른 무료 API를 조사해봤어요(2026-08 기준):
     - **Groq**(선택): 신용카드 등록 없이 무료 가입만으로 모델별로 하루 약 1,000회 안팎까지 쓸 수 있어요(Gemini의 약 50배) — 이번에 새로 연동했어요.
     - OpenRouter: 결제 이력이 전혀 없으면 하루 50회, 계정에 10달러 이상 충전한 이력이 있으면(1회성, 매달 다시 낼 필요 없음) 하루 1,000회로 늘어나요. 여러 모델(Llama·Gemma·DeepSeek·Qwen 등)을 한 창구로 쓸 수 있어요. 지금은 굳이 추가 연동하지 않았어요 — Groq 하나로도 충분히 넉넉해서, 계정을 하나 더 관리하는 번거로움을 늘리지 않는 게 낫다고 판단했어요. 나중에 Groq마저 부족해지면 이 옵션을 추가로 붙일 수 있어요.
     - **클로드(Anthropic) API는 상시 무료 등급이 없어요** — 신규 가입 시 테스트용 소액 크레딧을 한 번 주긴 하지만, 그 이후로는 계속 유료(사용한 만큼 과금)예요. 그래서 이번 조사에서는 무료 폴백 후보에서 제외했어요.
     - 그래서 **Groq를 새로 연동**했고(`src/lib/groq.ts`), 위 3번 채팅 기능뿐 아니라 **기존 위키/퀴즈 자동 생성의 폴백 순서에도 끼워 넣었어요**: 이제 Gemini 할당량을 다 쓰면 **Groq(우선) → 그다음 로컬 Ollama** 순서로 자동으로 넘어가요(`src/lib/gemini.ts`, `src/lib/quiz-gemini.ts`). Groq를 먼저 시도하는 이유는 Ollama와 달리 Groq는 인터넷 너머의 클라우드 API라서, 로컬 개발 중에도 배포된 사이트(Vercel)에서도 똑같이 동작하기 때문이에요(Ollama는 "지금 이 서버 코드가 돌아가는 컴퓨터"에서만 되니까, 배포 환경에선 무용지물이었어요). `/quiz/select`의 생성 진행 메시지에도 "Groq로 만든 것 N개 포함"이 표시돼서 실제로 어느 경로로 만들어졌는지 알 수 있어요.
     - Groq를 안 쓰고 싶으면 `.env.local`에 `GROQ_API_KEY`를 그냥 안 넣으면 돼요 — 채팅 위젯은 "설정 안 됨" 안내만 뜨고, 자동 생성은 예전처럼 Gemini→Ollama만 시도해요(오류 없이 조용히 건너뛰어요).
     - Groq 호출 코드는 실제 API 키가 있는 환경에서만 살아있는 서버로 테스트할 수 있어서(이 환경엔 인터넷으로 나가는 실제 키가 없음), 요청·응답 형식과 에러 처리(할당량 초과·설정 안 됨·일반 오류 구분)는 코드로 검증했지만, 실제 응답 품질은 `GROQ_API_KEY`를 넣고 직접 한 번 확인해주셔야 해요.
- 아직 안 된 것: 문서 추가·삭제 화면, 이미지 업로드/리사이즈, 이미지 인식·관계 퀴즈. 원하시면 로드맵과 별개로 추가 요청해주시면 돼요.

## 시작하려면 (당신이 해야 하는 부분)

1. **Supabase 프로젝트 만들기**: https://supabase.com → 무료 플랜으로 새 프로젝트 생성 (이메일/GitHub 로그인, 몇 분이면 끝나요). 생성 화면의 **Security** 옵션은 이렇게 설정하세요.
   - **Enable Data API**: 켜짐 유지. 이 앱은 `@supabase/supabase-js`로 REST API(Data API)를 통해 DB에 접근하므로 꺼지면 아예 연결이 안 됨.
   - **Automatically expose new tables**: **꺼두는 걸 권장** (Supabase도 "manually control access"를 권장). 이 옵션을 켜두면 RLS 정책이 있어도 새 테이블이 API에 기본 노출됨 — 꺼두면 `schema.sql`에 이미 포함된 명시적 `GRANT` 문(아래 참고)이 대신 권한을 준다. 로컬 Postgres로 직접 검증함: GRANT 없이는 RLS를 통과해도 "permission denied"가 나고, GRANT를 추가하니 로그인한 본인 행만 정상 접근되고 `anon`(비로그인) 역할은 여전히 막히는 것까지 확인했음.
   - **Enable automatic RLS**: **켜두는 걸 권장**. `schema.sql`이 이미 모든 테이블에 RLS를 명시적으로 켜두지만, 나중에 대시보드에서 테이블을 즉흥적으로 하나 더 만들 때 깜빡하고 RLS를 안 켜는 실수를 막아주는 안전장치라 켜서 손해 볼 게 없음.
2. **스키마 적용**: Supabase 대시보드 → SQL Editor → `supabase/schema.sql` 내용을 붙여넣고 실행. (Automatically expose new tables를 꺼뒀다면 이 파일 안의 `grant ... to authenticated` 구문이 접근 권한까지 같이 설정해줌.) 그다음 새 쿼리 창에서 `supabase/storage.sql`도 실행 — 파일 업로드용 Storage 버킷을 만들어요. **이미 위 두 파일을 실행해서 Phase 3까지 써봤다면**, 새 쿼리 창에서 `supabase/migrations/002_phase4_pending_changes.sql`만 추가로 실행하세요(스키마 파일 전체를 다시 실행하면 "이미 존재하는 표" 오류가 나요 — 이 마이그레이션 파일 하나만 실행하면 됩니다).
3. **키 확인**: 프로젝트 설정 → API 메뉴에서 Project URL, `anon` `public` 키, `service_role` 키를 확인.
4. **환경변수 설정**: Supabase 사이트가 아니라 **이 프로젝트 폴더 안에서** 하는 작업이에요. `study-wiki-app` 폴더(= `package.json`이 있는 바로 그 폴더) 안에 있는 `.env.local.example` 파일을 같은 위치에 **`.env.local`**이라는 이름으로 복사한 뒤, 메모장 같은 텍스트 편집기로 열어서 3번에서 확인한 값들을 채워넣으면 돼요.
   - 터미널이 편하면: 프로젝트 폴더에서 `cp .env.local.example .env.local` 실행 후 `.env.local`을 편집기로 열기.
   - `.env.local`은 내 컴퓨터에만 있는 파일이라 깃에도 안 올라가고 Supabase 쪽에 뭘 입력하는 게 아니에요 — 나중에 배포할 때(Vercel)는 그 사이트의 프로젝트 설정 화면에 같은 값들을 한 번 더 등록하게 됩니다.
   - **Gemini API 키**(`GEMINI_API_KEY`)는 https://aistudio.google.com 에서 무료 발급받아 `.env.local`에 채워넣으세요. 이미 Phase 3까지 써봤다면 기존 `.env.local`에 이 줄만 추가하면 돼요.
5. **이메일 로그인 설정**: Supabase 대시보드 → Authentication → Providers에서 Email(매직 링크)이 켜져 있는지 확인. Authentication → URL Configuration에 배포 후 도메인(또는 로컬 개발 중엔 `http://localhost:3000/**`)을 Redirect URLs에 추가.
6. 로컬 실행: `npm install` (Phase 4용 `@google/genai` 패키지가 새로 추가됐으니 이미 Phase 3까지 설치했더라도 한 번 더 실행해주세요) → `npm run dev` → http://localhost:3000 에서 로그인 → `/api/dev-check`로 저장/조회가 실제로 되는지 확인 (Phase 2 완료 기준).
7. **Phase 3 확인**: `/upload`로 이동해서 워크북 PDF 아무거나 하나 올려보세요. "N페이지 · 청크 N개" 메시지가 뜨면 성공이에요. Supabase 대시보드 → Table Editor → `text_chunks`에서 실제로 조각난 텍스트가 들어갔는지, `source_files`의 `status`가 `extracted`인지 봐도 좋아요.
8. **Phase 4 확인**: 업로드 성공 메시지 아래에 뜨는 "AI로 위키 문서 생성 시작" 버튼을 누르세요. "생성 중..."이 뜨다가 "생성 완료"로 바뀌면 끝이에요 — 새 문서 개수와 승인 대기 개수가 같이 표시돼요.
   - Supabase 대시보드 → Table Editor → `wiki_pages`에서 실제로 문서가 생성됐는지 확인해보세요.
